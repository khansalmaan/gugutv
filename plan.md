# Watch Party --- Implementation Plan

## 1. Project Goal

Build a Chrome/Chromium browser extension plus a Go WebSocket backend
that allows two or more users to watch the same HTML5 video in sync.

The first version should be intentionally simple:

-   Users join the same room.
-   Each browser independently plays the video from its streaming
    provider.
-   The extension listens for local `play`, `pause`, and `seeked`
    events.
-   Local events are sent through a WebSocket connection to the Go
    server.
-   The server broadcasts events to the other members of the room.
-   Other browsers apply the remote event to their local video.
-   Synchronization is bidirectional: every participant can control
    playback.
-   Accept up to roughly 1 second of synchronization latency/drift for
    the MVP.
-   Do not implement sophisticated clock synchronization or
    playback-rate correction in the MVP.
-   Start by testing against ordinary HTML5 video.
-   Keep the player integration isolated so provider-specific behavior
    can be added later.

The project is not intended to proxy, download, decrypt, or restream
video content. Video bytes should continue to come directly from the
original website.

# 2. Technology Choices

## Backend

-   Go
-   WebSocket library: `github.com/gorilla/websocket`
-   Standard library HTTP server
-   In-memory room state for MVP
-   No database
-   No authentication
-   JSON WebSocket messages

## Extension

-   Chrome/Chromium Extension
-   Manifest V3
-   Plain JavaScript
-   No frontend framework initially
-   Content script for DOM/video interaction
-   Background service worker for WebSocket/network coordination
-   Popup UI for room ID and sync controls

## Testing

-   Go unit tests for room/client behavior
-   Browser/manual testing with a local HTML5 video test page
-   Chrome extension loaded as an unpacked extension

Important architectural rule:

**The Go server is a relay/state service. It does not stream video.**

The video remains on the user's browser.

# 5. WebSocket Protocol

Use JSON messages.

Every synchronization event should have:

``` json
{
  "id": "uuid",
  "senderId": "client-uuid",
  "roomId": "room-id",
  "type": "PLAY",
  "position": 123.45,
  "timestamp": 1726742300123
}
```

Fields:

-   `id`: unique event ID generated by sender.
-   `senderId`: persistent ID for the extension installation/session.
-   `roomId`: room the event belongs to.
-   `type`: `PLAY`, `PAUSE`, or `SEEK`.
-   `position`: video position in seconds.
-   `timestamp`: Unix milliseconds when event was generated.

The server should preserve the message and add a monotonically
increasing room sequence number:

``` json
{
  "id": "uuid",
  "senderId": "client-a",
  "roomId": "room-123",
  "type": "PLAY",
  "position": 123.45,
  "timestamp": 1726742300123,
  "sequence": 42
}
```

The sequence number provides deterministic ordering within a room.

# 6. Room Model

For the MVP, maintain rooms in memory.

Conceptually:

``` go
type Room struct {
    ID      string
    Clients map[string]*Client
    Mu      sync.RWMutex
}
```

A room should support:

-   add client
-   remove client
-   broadcast event to all clients except sender
-   maintain sequence number
-   retrieve current state

Use a central room manager:

``` go
type RoomManager struct {
    Rooms map[string]*Room
    Mu    sync.RWMutex
}
```

Room IDs can be short human-friendly strings, for example:

``` text
ABCD12
```

Do not require a database for MVP.

------------------------------------------------------------------------

# 7. Client Model

Each WebSocket connection should be represented by a client:

``` go
type Client struct {
    ID   string
    Room *Room
    Conn *websocket.Conn
    Send chan []byte
}
```

Use a dedicated write loop per client.

Do not allow multiple goroutines to write directly to the same WebSocket
connection.

Recommended pattern:

``` text
readPump()
    |
    v
room / server

writePump()
    ^
    |
Send channel
```

This avoids concurrent WebSocket writes.

# 8. WebSocket Connection Lifecycle

When an extension connects:

``` text
WS CONNECT
    |
    v
Authenticate/validate room ID
    |
    v
Create/find room
    |
    v
Register client
    |
    v
Start readPump + writePump
```

For MVP, room joining can happen through the WebSocket URL:

``` text
ws://localhost:8080/ws?room=ABC123&clientId=...
```

Validate:

-   room ID exists/is valid format
-   client ID is present
-   message sizes are bounded

Do not implement real authentication yet.

# 9. Event Broadcasting

When the server receives:

``` json
{
  "type": "PAUSE",
  "position": 1523.42
}
```

it should:

1.  Validate the message.
2.  Verify the sender belongs to the room.
3.  Assign the next sequence number.
4.  Broadcast to all other clients in the room.
5.  Do not send the event back to the sender.

Example:

``` text
Alice
  |
  | PAUSE
  v
Server
  |
  +----> Bob
  |
  +----> Charlie
```

Do not create server-side feedback loops.

------------------------------------------------------------------------

# 10. Room State

The MVP should maintain the latest canonical room state.

``` go
type PlaybackState struct {
    Type      string
    Position  float64
    Timestamp int64
    Sequence  uint64
}
```

The latest state should be updated whenever a valid playback event
arrives.

This is important for reconnects.

If a new client joins a room, send it the latest state if one exists.

Example:

``` json
{
  "type": "STATE",
  "playback": "PLAY",
  "position": 542.31,
  "timestamp": 1726742300123,
  "sequence": 27
}
```

The client can then catch up.

# 11. Extension Architecture

Use three conceptual layers.

``` text
Popup
  |
  v
Background Service Worker
  |
  +---- WebSocket
  |
  +---- content-script messaging
  |
  v
Content Script
  |
  v
Video Player
```

## Content Script

Responsibilities:

-   Find video element.
-   Attach/detach playback listeners.
-   Convert local player actions into normalized events.
-   Receive remote events.
-   Apply remote events.
-   Prevent remote events from being emitted again.
-   Handle video element replacement.

## Background Service Worker

Responsibilities:

-   Maintain WebSocket connection.
-   Join/leave room.
-   Send events received from content script.
-   Forward received events to the active content script.
-   Handle reconnection.
-   Maintain client/session ID.

## Popup

Responsibilities:

-   Enter room ID.
-   Join room.
-   Leave room.
-   Enable sync.
-   Disable sync.
-   Show connection state.
-   Show room ID.

# 13. Content Script --- Video Detection

The content script should find the active HTML5 video.

Initial implementation:

``` js
document.querySelector("video")
```

But websites can dynamically create or replace the video element.

Use a `MutationObserver` to detect video elements.

Requirements:

-   If no video exists, wait.
-   When a video appears, attach listeners.
-   If the video element is replaced, remove listeners from the old
    element and attach them to the new one.
-   Never attach duplicate listeners to the same element.

Track the currently attached element:

``` js
let currentVideo = null;
```

------------------------------------------------------------------------

# 14. Content Script --- Event Listeners

Listen to:

``` text
play
pause
seeked
```

Do not use `seeking` as the network synchronization event in the MVP
because dragging a timeline can generate many `seeking` events.

Use `seeked` once the seek operation has completed.

Example:

``` js
function onPlay() {
    emitLocalEvent({
        type: "PLAY",
        position: video.currentTime
    });
}

function onPause() {
    emitLocalEvent({
        type: "PAUSE",
        position: video.currentTime
    });
}

function onSeeked() {
    emitLocalEvent({
        type: "SEEK",
        position: video.currentTime
    });
}
```

------------------------------------------------------------------------

# 15. Preventing Feedback Loops

This is a mandatory requirement.

Bad flow:

``` text
A pauses
 -> server
 -> B receives PAUSE
 -> B calls video.pause()
 -> B's pause listener fires
 -> B sends PAUSE
 -> A receives PAUSE
 -> ...
```

Use a guard:

``` js
let applyingRemoteEvent = false;
```

When applying a remote event:

``` js
applyingRemoteEvent = true;

video.currentTime = event.position;
video.pause();

applyingRemoteEvent = false;
```

Local listeners must check:

``` js
if (applyingRemoteEvent) {
    return;
}
```

Use `try/finally` so the flag is always reset:

``` js
applyingRemoteEvent = true;

try {
    // apply event
} finally {
    applyingRemoteEvent = false;
}
```

------------------------------------------------------------------------

# 16. Applying Remote Events

For:

``` text
PLAY
```

perform:

``` js
video.currentTime = event.position;
await video.play();
```

Handle the possibility that `video.play()` rejects.

For:

``` text
PAUSE
```

perform:

``` js
video.currentTime = event.position;
video.pause();
```

For:

``` text
SEEK
```

perform:

``` js
video.currentTime = event.position;
```

Do not attempt sophisticated latency compensation in the MVP.

# 17. Event Deduplication

Track recently processed event IDs.

For example:

``` js
const processedEvents = new Set();
```

Before processing:

``` js
if (processedEvents.has(event.id)) {
    return;
}

processedEvents.add(event.id);
```

Keep the set bounded, for example to the latest 1000 IDs.

This protects against duplicate WebSocket deliveries or
reconnect-related duplication.

------------------------------------------------------------------------

# 18. Sender ID

Generate a client ID when the extension first runs.

Prefer storing it using:

``` js
chrome.storage.local
```

Example:

``` text
clientId = UUID
```

Every event should contain:

``` json
{
  "senderId": "..."
}
```

The receiver should ignore events whose sender ID is its own ID.

The server should also avoid broadcasting to the sender.

------------------------------------------------------------------------

# 19. Bidirectional Sync

There is no permanent host.

Both clients run identical logic.

``` text
A local action
    ↓
send event
    ↓
server
    ↓
B receives
    ↓
apply event
```

And:

``` text
B local action
    ↓
send event
    ↓
server
    ↓
A receives
    ↓
apply event
```

Both are allowed to control playback.

------------------------------------------------------------------------

# 20. Concurrent Events

For MVP, resolve simultaneous events using server arrival order.

Example:

``` text
sequence 101 -> PAUSE
sequence 102 -> SEEK
```

Clients process sequence order.

Do not implement CRDTs, vector clocks, distributed locks, or advanced
conflict resolution.

The expected user experience is informal watch-party synchronization,
not strict distributed transaction semantics.

------------------------------------------------------------------------

# 21. Synchronization Tolerance

Target:

**approximately \<= 1 second of normal synchronization error.**

Do not implement:

-   clock synchronization
-   NTP-like correction
-   continuous server heartbeat position correction
-   playback-rate adjustment
-   PID controllers
-   continuous seeking

Those can be added later if needed.

The event should contain:

``` text
position
timestamp
```

The timestamp is useful for future improvements even though the MVP may
not use it for compensation.

------------------------------------------------------------------------

# 22. Reconnection

The WebSocket client must automatically reconnect.

Suggested backoff:

``` text
1 second
2 seconds
4 seconds
8 seconds
16 seconds
30 seconds max
```

Reset the backoff after a successful connection.

When reconnected:

1.  Rejoin the room.
2.  Request current state.
3.  Apply current room state.
4.  Resume normal event processing.

Avoid generating local synchronization events while applying the
recovered state.

# 25. Security / Validation

Even though there is no authentication in MVP:

-   Validate room IDs.
-   Validate event types.
-   Validate `position >= 0`.
-   Reject absurd positions.
-   Limit WebSocket message size.
-   Limit number of clients per room to a reasonable development value.
-   Never allow arbitrary server-side commands from WebSocket messages.
-   Never execute received JavaScript.
-   Treat all received event data as untrusted.

Do not implement authentication yet.

# 27. Manual Test Plan

## Test 1 --- Connection

1.  Start Go server.
2.  Load extension.
3.  Open two browser windows.
4.  Join same room.
5.  Confirm both show `CONNECTED`.

Expected:

``` text
A: Connected
B: Connected
```

## Test 2 --- A controls B

1.  A presses play.
2.  B should start playing.
3.  A pauses.
4.  B should pause.
5.  A seeks.
6.  B should seek.

## Test 3 --- B controls A

Repeat the same actions from B.

## Test 4 --- Feedback loop

1.  A presses play.
2.  Confirm B plays.
3.  Confirm B does NOT emit a second PLAY back to A.
4.  Confirm no event storm occurs.

## Test 5 --- Repeated seeking

1.  Drag the timeline.
2.  Confirm the server isn't flooded with dozens/hundreds of `SEEK`
    events.
3.  Confirm one `SEEK` is sent after the seek completes.

## Test 6 --- Video replacement

1.  Replace/remove the video element.
2.  Insert a new video.
3.  Confirm listeners attach to the new element.
4.  Confirm old listeners are removed.

## Test 7 --- Disconnect/reconnect

1.  Start playback.
2.  Disconnect B's network.
3.  Wait several seconds.
4.  Restore connection.
5.  Confirm B reconnects.
6.  Confirm B obtains the latest room state.

## Test 8 --- Duplicate event

Send the same event twice.

Expected:

``` text
First event -> applied
Second event -> ignored
```

# 31. Error Handling

The extension must not crash if:

-   no video exists
-   video disappears
-   `video.play()` rejects
-   WebSocket disconnects
-   malformed server message arrives
-   popup is closed
-   content script is reloaded
-   user navigates to another page

All failures should degrade gracefully.

# 32. Important Chrome Extension Detail

The content script and background service worker are separate extension
contexts.

Use Chrome runtime messaging:

``` text
content.js
    ↕
chrome.runtime.sendMessage
    ↕
background.js
```

The background worker owns the WebSocket connection.

The content script owns the video/DOM.

Do not make the content script depend directly on DOM access from the
background worker.

------------------------------------------------------------------------

# 33. Provider Abstraction

Do not hard-code Netflix-specific logic into the synchronization
protocol.

Create a conceptual player adapter:

``` js
class VideoPlayerAdapter {
    findPlayer()
    attachListeners()
    removeListeners()
    getPosition()
    play(position)
    pause(position)
    seek(position)
}
```

Initial implementation:

``` text
HTML5VideoAdapter
```

Later:

``` text
NetflixAdapter
YouTubeAdapter
OtherProviderAdapter
```

The sync engine should not care where the video comes from.

# 38. Coding Guidelines

Keep the implementation simple and readable.

Prefer:

-   small functions
-   explicit state
-   clear message types
-   interfaces for player adapters
-   error handling
-   unit tests around state transitions

Avoid:

-   unnecessary abstractions
-   premature distributed infrastructure
-   framework-heavy frontend
-   global mutable state where avoidable
-   hidden retry loops
-   provider-specific code leaking into the core synchronization engine

The goal is a small, understandable codebase that can later evolve into
a production watch-party system.

# 39. Final Architecture Target

``` text
                           ┌────────────────────┐
                           │      Go Server     │
                           │                    │
                           │   Room Manager     │
                           │   Room State       │
                           │   WS Connections   │
                           └─────────┬──────────┘
                                     │
                         WebSocket   │   WebSocket
                    ┌────────────────┘ └────────────────┐
                    │                                   │
                    ▼                                   ▼
             ┌──────────────┐                    ┌──────────────┐
             │ Extension A  │                    │ Extension B  │
             │              │                    │              │
             │ Background   │                    │ Background   │
             │      ↕       │                    │      ↕       │
             │ Content      │                    │ Content      │
             │      ↕       │                    │      ↕       │
             │ Video Player │                    │ Video Player │
             └──────────────┘                    └──────────────┘

             Local actions                      Local actions
                  │                                  │
                  ▼                                  ▼
             PLAY/PAUSE/SEEK                    PLAY/PAUSE/SEEK
```

The central design principle is:

> **Synchronize playback state, not video data.**

Build the generic HTML5 implementation first. Once that works reliably,
provider-specific integration becomes a separate adapter problem rather
than something that contaminates the core architecture.
